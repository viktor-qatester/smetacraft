# Контракт JSON-проекта

Перед изменением прочитай `collectProject`, `parseProjectText`, `validateProjectV1`, `applyProject`, обработчик файла и функции `localStorage` в актуальном `index.html`, а также JSON-тесты. Сохраняй существующий формат `smetacraft-project`, числовую версию 1 и ключ `smetacraft_project`, пока задача явно не определит миграцию.

Проверяй полную границу до изменения DOM: обычный корневой объект, известные ключи и типы, ограничения файла/массивов, числовые значения, `locked` и правила неизвестных метаданных. Значения из файла не должны попадать в HTML-конструкторы; пользовательский текст записывай через `.value`/`.textContent`. Отказ должен сохранять `collectProject()` и не переписывать сохранённый проект. Явный boolean `opening.locked` сохраняй точно, а fallback используй лишь при отсутствии ключа; не переноси поведение проёмов на сваи без основания.

Проверь настоящий v1 round-trip, старые aliases `w/h/n`, валидный текстовый HTML-payload в `pile.name`, отказ payload в числовом поле, локальное хранилище и лимит 1 MiB до `readAsText`. Неизвестные top-level и секционные метаданные могут игнорироваться, но известный ключ с неверным типом должен отклонять импорт. Не меняй существующую NormalizedProjectModel, модульное деление или общий рефакторинг ведомости без отдельного задания.

Выход: таблица сохранённых/изменённых правил v1, доказательство атомарности, результаты `tests/security.test.cjs`, `tests/golden.test.cjs` и `tests/project-model.test.cjs`, ручной браузерный smoke-checklist для границ Node DOM-модели.
