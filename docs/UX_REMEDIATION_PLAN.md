# План точечных UX-исправлений SmetaCraft

Основание: E2E-проход 2026-09-18 по сценарию «дом 9×8 м → пять разделов → изменение цены → сводная → JSON export → reload → ответ backend». План описывает будущие отдельные задачи, а не разрешение на их реализацию. Статусы фаз остаются в `docs/ROADMAP.md`.

## Неизменяемые контракты

- Не менять формулы `js/core/*.js`, нормативные коэффициенты, округления, действующие строки/суммы и JSON v1 без отдельного согласования конкретного шага.
- Не переписывать `tests/golden.json` ради прохождения тестов. Новый вид ведомости получает собственные проверки; существующий вид и его golden остаются эталоном до отдельного решения.
- Сохранить `localStorage` и импорт/экспорт; не включать перенос проектов Phase 7 и постоянное хранилище Phase 8.
- Каждый шаг: узкий diff, `node --test tests/golden.test.cjs tests/security.test.cjs tests/project-model.test.cjs tests/backend.test.cjs`, `node scripts/validate-skills.cjs`, проверка синтаксиса, `git diff --check`, браузерный контроль через HTTP. Commit, push, PR и deploy — только по отдельному разрешению.

## Шаг 0. Закрыть проверочные пробелы Phase 6

Scope: только проверка, исправлять лишь воспроизведённый дефект отдельной задачей. Через реальный браузер пройти export → выбор скачанного JSON → восстановление полей, цен, проёмов, выбранных разделов и суммы; проверить печатный вид и PDF. Сверить с текущими Node-тестами и снимком контрольной ведомости. Phase 6 в `docs/ROADMAP.md` до решения владельца остаётся «ожидает приёмки».

Выход: протокол браузерной проверки с фактическими файлами/итогами и список воспроизводимых дефектов, если есть.

## Шаг 1. Освободить рабочий экран от диагностики

Scope: `index.html`, `js/app/regression.js`, при необходимости только текст и размещение `js/app/backend-check.js`. Успешные встроенные тесты показывать компактно или только в диагностике; ошибку оставить заметной. Серверную проверку обозначить как техническую проверку приёма, отдельно от сохранения проекта. Не менять запрос и ответ API.

Выход: на обычном экране нет перекрывающей ведомость полосы; ошибка встроенных тестов видна; серверный статус понятен; расчётные строки и сумма прежние. Проверить длинную ведомость и узкий экран.

## Шаг 2. Уточнить прайс-лист стен

Scope: сначала подтвердить по коду, какие `walls-*` цены относятся к `_readWallsFormLegacy`, а какие `wall-*` и `strip-rebar-price` используются действующим `readWallsForm`. В `index.html` явно разделить действующие и архивные/совместимые цены, свернуть вторые за пояснением. Не удалять и не переименовывать input ID: они участвуют в JSON v1 и тестах.

Выход: пользователь с первого взгляда находит цену, влияющую на текущие стены; изменение действующей цены пересчитывает стеновую ведомость, правка архивной не создаёт ложного ожидания; JSON round-trip и прежние суммы проходят.

## Шаг 3A. Отдельный подробный вид «Позиции к закупке»

Это изменение UI-контракта; утверждать его отдельно. На вкладке сводной добавить переключение между текущей «Сводкой затрат» и новым подробным списком. Новый список строить из уже рассчитанных `bill.rows` каждого включённого раздела, сохраняя `name/netLabel/k/orderLabel/cost`, исходный порядок внутри раздела и единицы. Разделить материалы и работы, показывать строки по разделам; одинаковые названия из разных разделов сначала не объединять, чтобы не смешать назначения и единицы. Не переносить денежную сумму в колонку «К заказу». Общий итог и суммы разделов сверить с прежней сводной; формулы не трогать. Текущий вид и golden оставить неизменными.

Затронутые места: `js/app/summary.js`, `js/app/bill.js`, разметка в `index.html`, порядок модулей в `tests/runtime.cjs` при добавлении файла, новые сценарные тесты. Вести работу по одному разделу: стены → штукатурка → кровля → перекрытия, после каждого сверять строки и итог. Фундамент уже выводит детальные строки.

Выход: технолог может выписать количество и единицу для каждой позиции без обхода отдельных вкладок; сумма полного проекта совпадает с прежней; ни один раздел не теряется и не удваивается. Браузерная проверка полного и частичного состава, плиты и ленты со сваями.

## Шаг 3B. Передача подробного результата

Только после приёмки 3A. Проверить печатную форму для нового вида: заголовок, состав объекта, позиции, количества, единицы, цены и итог читаемы на страницах без обрезания. При необходимости добавить отдельный экспорт закупочного списка как новую функцию; JSON проекта v1 не превращать в ведомость и не менять его схему. Уточнить подпись «предварительная ведомость» и границу применения.

Выход: получатель открывает PDF/распечатку и видит тот же состав и суммы, что на экране.

## Шаг 4. Различать файлы проектов

Scope: `js/app/project.js`, текст в `index.html`/README и тест экспорта. Формировать понятное имя скачиваемого файла из уже существующих данных, например дата + габариты, с безопасной нормализацией; в UI показывать фактическое имя. Не добавлять имя объекта в JSON v1 и не менять `localStorage` в этом шаге. Полноценная идентичность и перенос проектов относятся к отдельно согласуемой Phase 7.

Выход: два экспорта разных объектов различимы в папке загрузок; содержимое JSON и обратный импорт побайтно/по модели сохраняют действующий контракт.

## Порядок и решения владельца

Сначала принять или исправить Phase 6 и закрыть проверку шага 0. Шаги 1 и 2 независимы и малы. Шаг 3A — ключевое продуктовое решение о детальном представлении ведомости; шаг 3B зависит от его приёмки. Шаг 4 можно выполнять независимо после шага 0. Перед каждым изменением показать точный scope, контрольный пример и критерии; не выполнять весь план одной правкой и не начинать Phase 7 автоматически.
