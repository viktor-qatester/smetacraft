# Как поддерживать скиллы SmetaCraft

Скилл — короткая инструкция для повторяемого вида работы. Он помогает выбрать нужные проверки и границы задачи. Скилл не заменяет ваше разрешение на изменение кода, commit, push или deploy.

## Что читать и когда

| Источник | Что в нём хранить |
| --- | --- |
| `AGENTS.md` | Постоянные правила для всего репозитория. |
| `docs/ROADMAP.md` | Порядок, статус и границы фаз. |
| `.agents/skills/*/SKILL.md` | Когда применять конкретный процесс и как проверить результат. |
| `docs/regression-baseline.md` и тесты | Проверяемые расчётные и JSON-контракты. |

На старте фазы вызывайте `$smetacraft-phase-orchestrator`. Для Phase 5 вместе с ним подходит `$smetacraft-frontend-modules`. Если меняются формулы, данные проекта или тестовый контракт, используйте соответственно `$smetacraft-formula-audit`, `$smetacraft-project-json`, `$smetacraft-regression-tests`. Перед приёмкой diff — `$smetacraft-domain-review`.

После **принятой** фазы и до плана следующей вызывайте `$smetacraft-skill-maintenance`. Он проверяет, не устарели ли пути, контракты и условия применения. Мелкая правка кода сама по себе не требует переписывать скиллы.

## Когда создать новый скилл

Создавайте его, если появилась отдельная повторяемая работа со своими решениями и проверками, которую существующий скилл описывает плохо. Если изменился уже описанный процесс, исправьте старый скилл. Разовую задачу и текущий статус фазы в скилл не записывайте.

## Как сделать самостоятельно

1. Назовите задачу и условие срабатывания: «Применять при …; не применять при …». Выберите имя из строчных латинских букв и дефисов, например `smetacraft-frontend-modules`.
2. Создайте `.agents/skills/<имя>/SKILL.md`. Минимальный шаблон:

   ```md
   ---
   name: smetacraft-example
   description: "Что делает скилл и когда его применять. Укажите близкую задачу, где он не нужен."
   ---

   # Название

   Прочитай необходимые файлы. Определи границы и неизменные контракты.
   Выполни только согласованный scope. Проверь конкретный результат.
   Покажи diff и ограничения; публикацию выполняй по разрешению владельца.
   ```

3. Уберите общие советы, которые Codex и так знает. Оставьте факты проекта, опасные границы, проверки и критерии завершения. Подробную справку вынесите в `references/` лишь тогда, когда она нужна не в каждом запуске.
4. Проверьте структуру и локальные ссылки из корня репозитория:

   ```text
   node scripts/validate-skills.cjs
   git diff --check
   ```

   Валидатор проверяет обязательные поля `SKILL.md`, имена папок и локальные ссылки. Если установлен Python с `PyYAML`, можно дополнительно запустить `skill-creator/scripts/quick_validate.py` для выбранного скилла.

5. Проверьте смысл на двух мысленных запросах: подходящий запрос должен вызвать скилл, похожий, но посторонний — нет. Затем попросите Codex применить `$<имя>` к реальной небольшой задаче и оцените результат. Исправляйте только выявленный недостаток.

Памятка на границе фаз: **принять результат → обновить `ROADMAP` → проверить скиллы → составить план следующей фазы**. Следующую фазу не начинать только потому, что её скилл уже написан.
