# SmetaCraft: план подключения домена и перехода на HTTPS

**Статус:** будущая инфраструктурная задача, не выполнена.

**Дата подготовки:** 2026-09-22.

**Требование запуска:** не выполнять без явного разрешения владельца и выбранного домена.

Этот документ — инструкция для владельца, Cursor и Codex. Он описывает безопасный перенос публичного SmetaCraft с HTTP по IP-адресу на HTTPS по доменному имени. Документ не является разрешением менять сервер, DNS, код, GitHub или начинать Phase 9.

## 1. Текущая подтверждённая точка

- Репозиторий: `viktor-qatester/smetacraft`, ветка `master`.
- VPS Fornex: Ubuntu 24.04, IP `31.172.78.193`.
- Текущий публичный адрес тестеров: `http://31.172.78.193/`.
- Node.js сейчас рассчитан на прямой публичный запуск на порту `80`.
- Разрешённые origin заданы одновременно:
  - на сервере — `SMETACRAFT_PUBLIC_ORIGIN` в `/etc/smetacraft.env`;
  - в клиенте — `<meta name="smetacraft-public-origin">` в `index.html`.
- SQLite и загруженные файлы находятся в `/opt/smetacraft/data/` и не должны быть удалены или заменены при переходе.
- GitHub Pages остаётся статической копией без серверного API и не становится production-хостом.

Перед работой агент обязан подтвердить фактическое состояние VPS. Этот раздел может устареть.

## 2. Целевое состояние

Пример ниже использует условный домен `smetacraft.by`. Перед выполнением заменить его на домен, который фактически купил и подтвердил владелец.

```text
браузер пользователя
  -> https://smetacraft.by:443
  -> Nginx на VPS
  -> http://127.0.0.1:8000
  -> Node.js SmetaCraft
  -> SQLite и закрытое файловое хранилище
```

Обязательные свойства результата:

1. `https://smetacraft.by/` открывает приложение с валидным TLS-сертификатом.
2. `http://smetacraft.by/` перенаправляется на HTTPS.
3. Node.js слушает только `127.0.0.1:8000`, а не публичный интерфейс.
4. Публичные порты — `80` для перенаправления и проверки сертификата, `443` для HTTPS; SSH остаётся доступен.
5. Перенос проектов, readback, загрузка, preview, применение и удаление PDF/DOCX работают через HTTPS.
6. Формулы, строки ведомости, цены, golden baseline, SQLite-схема и сохранённые данные не меняются.
7. SmetaCraft автоматически запускается после перезагрузки VPS.
8. Сертификат автоматически продлевается.

## 3. Решения владельца до начала

До любых изменений агент должен получить и записать ответы:

- точное доменное имя;
- подтверждение, что домен оплачен и принадлежит владельцу;
- основной адрес: рекомендуется `https://smetacraft.by`;
- судьба `www`: рекомендуется перенаправлять `https://www.smetacraft.by` на основной адрес;
- разрешение на изменения DNS;
- разрешение на изменения VPS;
- отдельное разрешение на commit/push, если потребуется изменить `index.html`, тесты или документацию.

Не угадывать домен и не использовать пример `smetacraft.by`, пока его доступность и покупка не подтверждены.

## 4. Границы задачи

### В scope

- DNS-записи домена;
- Nginx как reverse proxy;
- бесплатный TLS-сертификат Let's Encrypt;
- перевод Node.js на `127.0.0.1:8000`;
- `SMETACRAFT_PUBLIC_ORIGIN` и клиентский список origin;
- HTTP -> HTTPS redirect;
- автозапуск, продление сертификата, техническая и браузерная проверка;
- обновление deployment-документации после успешного переноса.

### Вне scope

- изменение строительных формул и Calculation Core;
- изменение golden baseline ради прохождения тестов;
- изменение схемы SQLite;
- удаление `localStorage`, проектов, базы или загруженных файлов;
- аккаунты, billing, Phase 9 и AI;
- покупка платного сертификата без отдельного решения;
- смена VPS-провайдера;
- push, PR или deploy без явного разрешения владельца.

## 5. План выполнения

Каждый шаг выполняется отдельно. После ошибки остановиться, сохранить диагностику и не переходить дальше автоматически.

### Шаг 1. Preflight без изменений

Проверить и зафиксировать:

- `git status`, текущий commit и соответствие VPS ветке `master`;
- `node --version`;
- `systemctl status smetacraft --no-pager`;
- `systemctl is-enabled smetacraft`;
- `ss -ltnp` — какой процесс слушает порты `80`, `443`, `8000`;
- `ufw status` и firewall в панели Fornex;
- содержимое `/etc/smetacraft.env` без публикации секретов;
- свободное место `df -h`;
- ответ `curl -sSI http://127.0.0.1/` и текущего публичного адреса;
- полный локальный набор тестов репозитория: `node --test tests/*.test.cjs`.

Если сервис запущен через `nohup`, а не `systemd`, сначала согласовать перевод на `systemd`.

### Шаг 2. Резервная копия и точки отката

До изменения сервера:

- сделать датированную копию `/opt/smetacraft/data/`;
- скопировать `/etc/smetacraft.env`;
- сохранить текущий systemd unit;
- сохранить существующие конфиги Nginx, если Nginx уже установлен;
- записать текущие DNS-записи и TTL;
- проверить, что копия SQLite и каталог blobs присутствуют в бэкапе.

Не хранить серверные env, capability tokens, SSH-пароли, приватные ключи и содержимое пользовательских проектов в Git.

### Шаг 3. DNS

У регистратора создать записи:

| Тип | Имя | Значение |
| --- | --- | --- |
| `A` | `@` | `31.172.78.193` |
| `A` или `CNAME` | `www` | `31.172.78.193` или основной домен |

Перед выдачей сертификата проверить DNS через `dig` или `nslookup` из внешней сети. Оба имени должны указывать на текущий IP VPS. DNS может распространяться от нескольких минут до суток; ожидание не является дефектом приложения.

### Шаг 4. Подготовка кода и allowlist

Сначала временно разрешить одновременно старый HTTP-origin и новый HTTPS-origin, чтобы сохранить путь отката:

```text
http://31.172.78.193,https://smetacraft.by,https://www.smetacraft.by
```

Список должен быть одинаково согласован:

- в `/etc/smetacraft.env` на VPS;
- в `<meta name="smetacraft-public-origin">` в `index.html`;
- в тестах origin/host, если контракт изменён.

После успешной приёмки отдельным маленьким изменением убрать устаревшие публичные HTTP-origin. Не удалять их до доказанного HTTPS smoke-test.

До deploy изменения репозитория обязаны пройти полный набор тестов. Не обновлять `tests/golden.json`, если расчётное поведение не менялось.

### Шаг 5. Nginx и внутренний Node.js

Подготовить Nginx-конфигурацию для домена с:

- `server_name smetacraft.by www.smetacraft.by`;
- `client_max_body_size` не меньше действующего лимита приложения;
- proxy на `http://127.0.0.1:8000`;
- передачей `Host`, `Origin`, `X-Forwarded-For` и `X-Forwarded-Proto`;
- запретом выдачи `/opt/smetacraft/data/` как статических файлов.

Изменить `/etc/smetacraft.env`:

```text
PORT=8000
SMETACRAFT_BIND=127.0.0.1
SMETACRAFT_PUBLIC_ORIGIN=https://smetacraft.by,https://www.smetacraft.by
```

Во время перехода допускается временно оставить старый HTTP-origin в allowlist по плану шага 4.

Порядок переключения должен минимизировать простой: проверить конфиг Nginx, перевести Node.js на внутренний порт, сразу запустить Nginx и проверить оба процесса. Не оставлять Node.js публично доступным на `8000`.

### Шаг 6. TLS-сертификат

После подтверждения DNS выпустить бесплатный сертификат Let's Encrypt для основного домена и `www` через Certbot/Nginx.

Проверить:

- сертификат выдан именно на согласованные имена;
- приватный ключ находится только на VPS и не попал в Git;
- HTTP перенаправляется на HTTPS;
- `certbot renew --dry-run` проходит;
- systemd timer автоматического продления включён.

Не использовать самоподписанный сертификат для публичной версии.

### Шаг 7. Firewall и автозапуск

- не закрывать SSH до подтверждения второго рабочего SSH-сеанса;
- разрешить `80/tcp` и `443/tcp`;
- не открывать публично `8000/tcp`;
- подтвердить `systemctl enable smetacraft` и автозапуск Nginx;
- перезагрузку VPS выполнять только по отдельному разрешению, после всех проверок без reboot.

### Шаг 8. Проверка

#### Автоматическая

- `node --test tests/*.test.cjs` — все тесты проходят;
- `nginx -t` — конфигурация валидна;
- `curl -sSI http://smetacraft.by/` — redirect на HTTPS;
- `curl -sSI https://smetacraft.by/` — `200`;
- сертификат валиден, домен совпадает, срок действия корректен;
- прямой публичный доступ к `:8000` отсутствует;
- `/data/`, SQLite и blobs не выдаются статически.

#### Ручная в браузере

1. Открыть основной HTTPS-адрес без предупреждения браузера.
2. Проверить отсутствие mixed content и ошибок TLS в DevTools.
3. Выполнить контрольный расчёт и сверить строки и итог ведомости.
4. Проверить localStorage и JSON export/import.
5. Перенести копию проекта на сервер и выполнить readback.
6. Загрузить допустимый PDF/DOCX, открыть preview, применить параметры и удалить файл.
7. Убедиться, что цены не импортировались и формулы не изменились.
8. Проверить мобильное открытие не из домашней Wi-Fi-сети.
9. Выключить домашний компьютер и подтвердить, что сайт продолжает работать.

## 6. Критерии завершения

Задача принимается только если:

- домен и HTTPS работают извне;
- HTTP всегда перенаправляется на выбранный канонический HTTPS-адрес;
- браузер доверяет сертификату;
- Node.js недоступен извне напрямую;
- API не возвращает `origin_forbidden` для рабочего домена;
- ключевые пользовательские потоки пройдены;
- все автотесты зелёные;
- база и файлы сохранены;
- проверены автозапуск и автоматическое продление сертификата;
- документация обновлена фактическими значениями;
- владелец дал явное подтверждение приёмки.

## 7. Откат

Если HTTPS-переход не прошёл:

1. Сохранить точную ошибку, вывод проверок и текущие конфиги.
2. Не менять DNS хаотично и не выпускать повторно сертификаты без причины.
3. Остановить Nginx, если он занимает порт `80`.
4. Восстановить предыдущий `/etc/smetacraft.env` с `PORT=80` и `SMETACRAFT_BIND=0.0.0.0`.
5. Восстановить предыдущий systemd/Nginx-конфиг.
6. Перезапустить `smetacraft` и проверить старый IP-адрес.
7. При повреждении данных остановить сервис и восстановить только из проверенного бэкапа.

Не использовать `git reset --hard`, не удалять `data/` и не откатывать несвязанные пользовательские изменения.
