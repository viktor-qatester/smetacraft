# Большой промт для автономной работы Cursor над SmetaCraft

Ниже находится готовый промт. Вставляй в Cursor целиком из корня репозитория SmetaCraft.

---

## ПРОМТ ДЛЯ CURSOR

Ты работаешь в репозитории **SmetaCraft** как ведущий разработчик продукта. Твоя задача — автономно продолжить развитие импорта строительных PDF: приложение должно извлекать из проекта подтверждаемые параметры, показывать пользователю предпросмотр с источниками и только после явного подтверждения подставлять безопасные значения в существующий калькулятор.

Работай долго и самостоятельно в пределах описанного scope. Не проси подтверждение каждого технического шага. Сначала изучи проект, затем составь внутренний план, реализуй его небольшими проверяемыми шагами, исправляй найденные в пределах scope ошибки, запускай тесты и выполняй финальное ревью. Вопрос владельцу задавай только при настоящем блокере, который нельзя безопасно решить по коду, документации и данным.

### 1. Разрешение владельца

Если владелец лично отправил тебе этот промт, считай это отдельным явным разрешением:

- реализовать описанный ниже ограниченный этап;
- создавать и изменять относящиеся к нему код, тесты и документацию;
- делать несколько небольших логичных commit’ов;
- после полного зелёного набора проверок отправить эти commit’ы в текущую удалённую ветку GitHub.

Это **не** разрешение на deploy, изменение DNS/домена, работу с production-секретами, удаление пользовательских данных, переписывание истории Git, force push, переход к коммерческой Phase 9, добавление оплаты/аккаунтов или изменение строительных формул. Для этого нужно отдельное прямое указание владельца.

### 2. Главная продуктовая цель

Пользовательский сценарий должен стать таким:

1. Пользователь загружает PDF строительного проекта.
2. SmetaCraft безопасно сохраняет и читает файл.
3. Система извлекает только явно обнаруженные факты: размеры, тип конструкции, материалы, классы бетона, параметры арматуры, сваи и другие поддержанные поля.
4. Для каждого найденного значения система хранит доказательство: документ, страница, фрагмент текста/область, единица, исходное и нормализованное значение, статус и понятную причину уверенности или сомнения.
5. Пользователь видит предпросмотр: что найдено, что не найдено, что требует проверки и куда предлагается подставить значение.
6. Ничего не попадает в форму молча. Только пользователь нажимает «Применить».
7. После применения существующий детерминированный Calculation Core считает ведомость как раньше.

Ключевой принцип:

`PDF → извлечённые факты с доказательствами → нормализация → предпросмотр → подтверждение пользователя → существующая модель проекта → существующий Calculation Core`

LLM/OCR/parser не считают смету и не придумывают строительные значения. Они могут только предложить факты. Формулы, коэффициенты, округления и стоимость остаются детерминированным JavaScript-кодом.

До редактирования:

1. Прочитай полностью:
   - `AGENTS.md`;
   - `PRODUCT_SPEC.md`;
   - `README.md`;
   - `docs/ROADMAP.md`;
   - `docs/PHASES_6_9_EXECUTION_PLAN.md`;
   - `docs/IMPORT_PDF.md`;
   - `docs/regression-baseline.md`;
   - `docs/FRONTEND_MODULES.md`;
   - `data/training/annotations/v0.1/README.md`;
   - `data/training/annotations/v0.1/validation_report.md`;
   - `data/training/annotations/v0.1/field_catalog.csv`;
   - `data/training/annotations/v0.1/annotations.json`;
   - текущие файлы `server/import/*`, `js/app/document-import.js`, `js/app/explicit-text.js`, `js/app/project.js` и соответствующие тесты.
2. Проверь `git status`, текущую ветку, remote и последние commit’ы. Не уничтожай чужие или незакоммиченные изменения.
3. Запусти исходный полный набор тестов:

   ```bash
   node --test tests/*.test.cjs
   node scripts/validate-skills.cjs
   node data/training/annotations/v0.1/validate_annotations.mjs
   git diff --check
   ```

4. Зафиксируй для себя исходное число тестов и уже существующее поведение. Если baseline падает до твоих изменений, отдели существующую проблему от своей работы и не маскируй её перезаписью golden.

### 4. Обязательно используй проектные skills

Прочитай и применяй skills выборочно, а не формально:

- `.agents/skills/smetacraft-phase-orchestrator/SKILL.md` — чтобы удержать этап и критерии выхода;
- `.agents/skills/smetacraft-file-import/SKILL.md` — для upload/parser/preview/apply;
- `.agents/skills/smetacraft-project-json/SKILL.md` — если меняется путь данных проекта или совместимость JSON;
- `.agents/skills/smetacraft-regression-tests/SKILL.md` — для тестовой стратегии;
- `.agents/skills/smetacraft-domain-review/SKILL.md` — для финального read-only ревью diff;
- `.agents/skills/smetacraft-skill-maintenance/SKILL.md` — только если реально устарели повторяемые инструкции skills.

Не применяй `smetacraft-formula-audit`, если формулы не менялись. Расчётные формулы в этом этапе менять нельзя.

Если доступен агентный режим Cursor, можно параллельно поручить отдельным агентам **read-only** анализ архитектуры, тестов, безопасности импорта и набора разметки. Главный агент обязан сам проверить выводы и отвечает за итоговый diff. Не разрешай агентам одновременно редактировать одни и те же файлы.

### 5. Разрешённый scope этапа

#### A. Сделать набор разметки исполняемым контрактом

- Используй `data/training/annotations/v0.1` как проверяемый эталон, а не как текстовую справку.
- Создай тестовый адаптер, который может прогонять parser по доступному PDF-корпусу и сравнивать результат с разметкой.
- Тесты обязаны различать:
  - `confirmed` — факт должен быть найден либо честно отмечен как пока неподдержанный;
  - `needs_review` — никогда не применять автоматически;
  - `not_found` — не превращать в `0`, пустую строку или выдуманное значение.
- Отдели качество извлечения от качества маппинга в поля калькулятора.
- Считай precision важнее recall: лучше не заполнить поле, чем уверенно подставить неверное.
- Не добавляй исходные PDF в Git, если манифест не подтверждает право на повторное распространение. Используй `dataset_manifest.csv`, контрольные суммы и локальный каталог корпуса.

#### B. Ввести нейтральную модель извлечённых фактов

Определи маленький документированный контракт наподобие:

```json
{
  "fieldId": "foundation.slab.thickness_mm",
  "rawValue": "h=200 мм",
  "normalizedValue": 200,
  "unit": "mm",
  "status": "confirmed",
  "confidence": 0.98,
  "source": {
    "objectId": "...",
    "page": 7,
    "evidence": "Монолитная ж/б плита h=200 мм"
  },
  "target": {
    "projectFieldId": "height",
    "conversion": "mm_to_m"
  },
  "warnings": []
}
```

Точное имя модели выбери по текущей архитектуре. Контракт должен быть детерминированно валидируемым, ограниченным по размеру, безопасным для пользовательского текста и независимым от DOM и Calculation Core.

#### C. Улучшить извлечение по доказанным типам документов

Начни с тех полей, которые одновременно:

- есть в разметке v0.1;
- имеют ясное текстовое доказательство;
- могут быть безопасно сопоставлены существующим полям SmetaCraft;
- не требуют инженерного вывода по геометрии чертежа.

Приоритет:

1. тип фундамента;
2. толщина плиты;
3. класс/марка бетона, только при доказуемом маппинге;
4. диаметры и шаг арматуры;
5. параметры свай: количество, диаметр/сечение, длина/глубина;
6. явные длина, ширина, высота и периметр;
7. явно напечатанные объёмы и массы как справочные extracted facts, но не как скрытая замена расчётным формулам.

Не пытайся на этом этапе «понимать глазами» произвольную геометрию плана, восстанавливать масштаб, вычислять размеры по линиям или строить универсальную CAD-модель.

Для scanned/image-only PDF добавь ясную границу OCR. Если в окружении уже есть безопасный локальный OCR, подключай его как отдельный адаптер с таймаутами и лимитами. Если зависимости нет, реализуй интерфейс и честный статус `ocr_required`/`unsupported`, но не добавляй тяжёлый облачный сервис, платный API или секреты без отдельного решения.

#### D. Сделать честный preview и безопасный apply

Предпросмотр должен показывать минимум:

- понятное название поля;
- найденное значение и единицу;
- страницу и короткое доказательство;
- целевое поле SmetaCraft;
- статус: подтверждено / проверить / не найдено / не поддерживается / конфликт;
- предупреждение о преобразовании единиц;
- checkbox или иной явный выбор, если пользователь может применить значение.

Правила apply:

- по умолчанию применять только выбранные пользователем строки;
- `needs_review`, конфликт и неподдержанные поля не выбирать автоматически;
- перед мутацией валидировать весь пакет;
- при одной критической ошибке не оставлять форму частично изменённой;
- не менять цены из PDF;
- не менять выбранную валюту прайс-листа;
- не удалять `localStorage` и не заменять проект молча;
- использовать безопасные DOM API (`textContent`, `.value`), не вставлять пользовательский текст через HTML;
- сохранять совместимость с существующим JSON v1 либо документировать и тестировать строго обратимо совместимое расширение.

#### E. Довести тесты до продуктового сценария

Добавь детерминированные проверки минимум для:

- корректного извлечения поддержанного поля с русским текстом;
- английского обозначения и явного преобразования единиц;
- десятичной запятой и десятичной точки;
- нескольких кандидатов одного поля и конфликта;
- значения без единицы;
- `not_found` без подстановки нуля;
- image-only PDF / необходимости OCR;
- повреждённого, слишком большого и неверного файла;
- evidence с HTML/скриптовой строкой без XSS;
- preview без изменения проекта;
- apply выбранных строк;
- отказ apply без частичной мутации;
- сохранения старого JSON/localStorage;
- неизменности расчётных строк, количеств и сумм после тех же подтверждённых входов.

Не копируй производственный parser в тест как «ожидаемый алгоритм». Используй явные fixtures и эталонную разметку.

### 6. Что запрещено

- Не менять формулы, нормы, запасы и округления в `js/core/*.js`.
- Не использовать LLM для расчёта сметы.
- Не подставлять догадки без доказательства из документа.
- Не превращать отсутствующее значение в ноль.
- Не применять поля без preview и явного действия пользователя.
- Не обновлять `tests/golden.json` просто ради зелёного теста. Любое намеренное изменение golden разбирай построчно и документируй.
- Не класть в Git PDF с неясными правами, секреты, `.env`, production-базу, загруженные пользовательские файлы и персональные данные.
- Не менять существующую валюту или цены при импорте строительного проекта.
- Не выполнять deploy и не трогать DNS.
- Не начинать Phase 9, auth, billing, подписки или аналитические трекеры.
- Не делать force push, rebase опубликованной истории, `reset --hard` или массовый рефакторинг «заодно».

### 7. Рабочая последовательность без участия владельца

Работай следующими вехами:

1. **Baseline и карта потока.** Опиши текущий путь upload → storage → parse → preview → apply и конкретные пробелы относительно разметки.
2. **Контракт facts.** Добавь модель, validation и unit tests.
3. **Dataset harness.** Подключи manifest/annotations и отчёт метрик без хранения спорных PDF в Git.
4. **Parser adapters.** Реализуй ограниченное извлечение приоритетных полей, сохраняя evidence и конфликты.
5. **Mapping.** Создай явную таблицу разрешённых соответствий extracted field → existing project field с преобразованием единиц.
6. **Preview/apply.** Улучши UI и атомарное применение.
7. **Security/limits.** Проверь размер, MIME/magic bytes, таймауты, path traversal, XSS и отказ без побочных эффектов.
8. **Full regression.** Запусти все тесты, skill validation, dataset validation, syntax checks и `git diff --check`.
9. **Browser smoke через HTTP.** Проверь upload → preview → выбор → apply, неверный файл, перезагрузку и восстановление проекта. Отдельно проверь смену валюты: символ меняется, числа не конвертируются, валюта сохраняется в проекте.
10. **Read-only review.** Примени `smetacraft-domain-review`, исправь findings в scope и повтори проверки.
11. **Документация.** Обнови только реально изменившиеся контракты и инструкции. Укажи ограничения и поддержанные поля без маркетинговых преувеличений.
12. **Commit и push.** Делай понятные небольшие commit’ы. Перед push проверь staged diff, отсутствие PDF/секретов/SQLite runtime-изменений и зелёные тесты. Затем обычный push без force.

После каждой вехи можешь сохранять короткий progress note в своей рабочей сессии, но не останавливайся в ожидании ответа, если следующий шаг однозначен и входит в scope.

### 8. Критерии завершения

Этап завершён только если одновременно выполнено всё:

- разметка v0.1 валидируется;
- parser выдаёт нейтральные факты с evidence и статусами;
- реализован ограниченный список доказанных маппингов;
- preview ничего не применяет сам;
- apply атомарен и не подставляет сомнительные/отсутствующие значения;
- цены и валюта не меняются импортом строительного PDF;
- JSON v1/localStorage остаются совместимыми;
- расчётные формулы и прежние результаты не изменились;
- полный набор `node --test tests/*.test.cjs` проходит;
- `node scripts/validate-skills.cjs` проходит;
- `node data/training/annotations/v0.1/validate_annotations.mjs` проходит;
- `git diff --check` проходит;
- браузерный smoke через HTTP пройден;
- финальное domain review не содержит незакрытых high/medium findings;
- документация честно перечисляет поддержанные поля и ограничения;
- commit’ы отправлены обычным push в согласованную текущую ветку;
- deploy не выполнялся.

### 9. Когда действительно нужно остановиться и спросить владельца

Остановись только если:

- требуется платный внешний API, секрет или регистрация сервиса;
- нужен deploy или изменение production/DNS;
- для правильного решения необходимо изменить строительную формулу;
- требуется несовместимая миграция JSON/БД или удаление данных;
- обнаружены незакоммиченные пользовательские изменения, которые невозможно безопасно обойти;
- права на нужные данные запрещают даже локальное использование;
- две продуктовые трактовки дают существенно разное поведение и код/документы не позволяют выбрать безопасную.

Во всех остальных случаях выбирай наиболее консервативное обратимо совместимое решение, фиксируй допущение в документации и продолжай.

### 10. Финальный отчёт владельцу

В конце дай короткий понятный отчёт на русском:

1. Что теперь умеет приложение глазами обычного пользователя.
2. Какие типы PDF и поля реально поддержаны, а какие пока нет.
3. Какие файлы и архитектурные контракты изменены.
4. Результаты тестов, dataset validation и browser smoke.
5. Список commit’ов и ветка, куда выполнен push.
6. Остаточные риски и один рекомендуемый следующий этап.

Не выдавай частичный прототип за универсальное распознавание всех строительных чертежей. Главное — проверяемость, безопасность и честный пользовательский контроль.
